# Playwright Framework Review Skill

## Purpose
Systematically review Playwright test files against HTDPlaywright2 framework standards, identifying defects, DRY violations, architecture misalignment, and coverage gaps with actionable remediation guidance.

## Scope & Outcomes
- **Workspace-scoped**: Enforces HTDPlaywright2 patterns (POM, actions, fixtures, testdata)
- **Review depth**: Standard (15-20 minutes, moderate depth)
- **Automation level**: Manual guided workflow with decision points
- **Output**: Severity-sorted findings + suggested code fixes

## Framework Standards Reference

### Architecture Layers (Enforcement Order)
1. **Page Objects** (`src/page/*.ts`): DOM locator definitions only
2. **Actions** (`src/action/*.ts`): Business logic using page objects
3. **Fixtures** (`src/fixture/*.ts`): Test setup, teardown, and shared constants
4. **Test Data** (`src/testdata/*.json`): Payloads, IDs, expected values
5. **Tests** (`tests/**/*.spec.ts`): Only orchestration logic using actions

### DRY Principles
- No duplicated selectors (must be in page objects)
- No duplicated test logic (must be in actions)
- No duplicated data (must be in testdata)
- No magic strings/numbers in tests (must be in testdata or fixtures)
- Reusable assertion patterns (helpers in `src/Utils/helper.ts`)

### Code Quality Standards
- Consistent test naming: `TC## - METHOD → Description`
- Strict assertions (not soft) unless explicitly documented
- Type-safe payloads matching testdata schema
- Array/response validation guards (type checks before property access)
- No debug code (console.log, commented code)
- No hard-coded URLs/endpoints (use fixtures)

## Review Workflow

### Phase 1: Scope & Context (2 min)

**User Input**: Which file(s) to review?
- Single test file (e.g., `tests/api/apiTest.spec.ts`)
- Test suite folder (e.g., `tests/Login/`)
- Entire test directory
- Specific test case name(s)

**Gather Context**:
```bash
1. Read target test file(s)
2. Identify corresponding page objects, actions, fixtures, testdata
3. Check for related existing utilities/helpers
4. Note framework version and dependencies
```

---

### Phase 2: Architecture Compliance Check (3 min)

**Scan for violations**:

| Layer | Red Flag | Fix Level |
|-------|----------|-----------|
| **Selectors in tests** | Hard-coded locators outside POM | Create/extend page object |
| **Business logic in tests** | Action sequences duplicated | Extract to action class |
| **Data in tests** | Magic strings, hard-coded IDs | Move to testdata.json |
| **Config in tests** | URLs, endpoints, constants | Move to fixture |
| **Helpers scattered** | Assertion logic in tests | Extract to src/Utils/helper.ts |

**Decision Point**: Are there architecture violations?
- **YES** → Document as HIGH/CRITICAL; add to Phase 5 recommendations
- **NO** → Proceed to Phase 3

---

### Phase 3: Code Quality Analysis (5-7 min)

#### 3.1 Assertion Consistency
Check each `expect()` statement:
```typescript
Pattern 1: expect.soft() → Flag if inconsistent with other tests
Pattern 2: toHaveProperty() → Shallow validation (flag if mixed with toMatchObject)
Pattern 3: toMatchObject() → Recommended for structure validation
Pattern 4: toEqual() → Too strict unless exact match required
Pattern 5: Custom assertions → Verify consistency
```

**Decision**: Are assertions mixed inconsistently?
- **YES** → HIGH severity; recommend standardization

#### 3.2 DRY Violation Detection
Search for:
- **Duplicated selectors**: Same `.locator()` calls in multiple tests → Move to page object
- **Duplicated payloads**: Same data shape/values → Extract to testdata.json
- **Duplicated assertions**: Same expect() patterns → Create assertion helper
- **Duplicated setup**: Same preconditions → Extract to fixture or shared function

**Count repetitions**:
- 1-2 instances → Low severity
- 3+ instances → MEDIUM/HIGH severity

#### 3.3 Test Data Management
Verify:
- [ ] All test payloads reference `src/testdata/*.json` or fixture
- [ ] No hard-coded IDs (use `testdata.ids` object)
- [ ] No magic strings (test descriptions, mock values, etc.)
- [ ] Payload schema matches actual API/app expectations

**Severity**:
- Magic strings in payloads → MEDIUM
- Hard-coded resource IDs → HIGH
- No testdata file structure → HIGH

#### 3.4 Debug Code & Hygiene
Scan for:
- `console.log()` statements → Remove
- Commented code → Remove unless documenting workaround
- TODOs without context → Flag
- Unused imports → Clean

**Severity**: LOW (cleanliness issue)

---

### Phase 4: Test Coverage Assessment (3-5 min)

#### 4.1 Positive Path Coverage
- Are all happy-path scenarios covered?
- Do tests exercise main user workflows?
- Is response structure validated?

#### 4.2 Negative/Edge Case Coverage
- **Are 4xx/5xx responses tested?** (Invalid IDs, missing fields, etc.)
- **Are boundary conditions tested?** (Empty arrays, null values, etc.)
- **Are error states tested?** (Network timeouts, malformed data, etc.)

#### 4.3 Type Safety Coverage
- Arrays checked before accessing `[0]`?
- Objects validated before property access?
- Response payloads match expected schema?

**Gaps Identified** → Document as coverage recommendations (MEDIUM severity if critical path)

---

### Phase 5: Generate Findings Report

**Structure findings by severity**:

#### CRITICAL Issues
- Soft assertions masking failures
- Type assumptions causing runtime errors
- Architecture violations (no separation of concerns)

#### HIGH Issues
- Duplicated logic/data (3+ instances of DRY violation)
- Hard-coded configuration
- Inconsistent assertion patterns

#### MEDIUM Issues
- Magic strings in payloads
- Missing error/edge case tests
- Incomplete response validation

#### LOW Issues
- Debug code leakage
- Style/naming inconsistencies
- Code cleanliness

**For Each Finding**:
```markdown
### [SEVERITY] Issue Title

**Location**: [file.ts](file.ts#L##)

**Current Code**:
\`\`\`typescript
[problematic code snippet]
\`\`\`

**Impact**: [Why is this a problem?]

**Suggested Fix**:
\`\`\`typescript
[corrected code]
\`\`\`

**Framework Alignment**: [Which standard is violated?]
```

---

### Phase 6: Decision & Next Steps (1-2 min)

**Present to user**:
1. Summary: X CRITICAL, Y HIGH, Z MEDIUM issues found
2. Critical/HIGH findings with suggested fixes
3. Approval checkpoints:
   - [ ] Approve architecture refactoring?
   - [ ] Approve DRY consolidations?
   - [ ] Approve assertion standardization?
   - [ ] Approve test data extraction?

**User Decision**:
- **Fix Now**: Execute approved changes (may spawn implementation subagent)
- **Review Later**: Export findings to file for future review
- **Discuss**: Clarify specific findings before proceeding

## Key Validation Checks

### Array Response Validation
```typescript
// ❌ UNSAFE: Assumes body[0] is an object
expect(body[0]).toHaveProperty('id');

// ✅ SAFE: Guards before property access
expect(Array.isArray(body)).toBeTruthy();
expect(body.length).toBeGreaterThan(0);
expect(typeof body[0]).toBe('object');
expect(body[0]).toHaveProperty('id');
```

### Assertion Consistency Pattern
```typescript
// ✅ RECOMMENDED: Type-safe with expectations
expect(body).toMatchObject({
  id: expect.any(Number),
  name: expect.any(String),
  email: expect.any(String),
});

// ⚠️ AVOID: Mixed patterns
expect(body.id).toBe(1);           // Exact match
expect(body).toHaveProperty('name'); // Just existence
```

### Test Data Extraction Pattern
```typescript
// ❌ BEFORE: Magic strings in test
const payload = { title: 'Avinash', userId: 1 };

// ✅ AFTER: Data in fixture/testdata
import { testData } from '../../testdata/api.json';
const payload = testData.payloads.createPost;
```

## Decision Tree for Severity Assignment

```
Does it cause test failure?
├─ YES, hard failure → CRITICAL
├─ YES, soft failure (masked) → HIGH
└─ NO → Continue

Is it a DRY violation (3+ duplicates)?
├─ YES → HIGH
└─ NO → Continue

Does it violate framework standards?
├─ YES, architectural → HIGH
├─ YES, code quality → MEDIUM
└─ NO → Continue

Does it reduce coverage or clarity?
├─ YES → MEDIUM
└─ NO → LOW (style/cleanliness)
```
